# 长截图自动滚动与预览方向优化设计

当前自动滚动用“连续 4 个重复采集帧”判断到达底部，但采集频率是 420 ms、滚动频率约 840 ms。一次滚动尚未完成时就可能先采到重复帧，因此两次没有及时观察到内容变化便会被误判为到底。对于微信、Codex、WorkBuddy 这类带固定输入框、异步渲染或惯性动画的窗口，这个判断尤其脆弱。预览倒置则来自合成阶段同时使用从上到下的条带坐标和翻转后的 Core Graphics 画布，生成的 CGImage 像素方向与 AppKit 预览方向不一致。

采用“滚动尝试状态机”替代重复帧阈值。每次自动滚动记录当时的有效帧数；随后采集若得到新增内容，则立即清零无进展次数。正常滚动延迟采用成熟工具常见的 300ms 级节奏，不再固定等待 1.3 秒。若画面仍重复，只在下一次真实发出滚动时累计一次无进展尝试，不再按每个采集 tick 累加。连续 2 次滚动均无新增内容后停止自动滚动，避免到底后持续把鼠标临时定位到选区中心。被 matcher 拒绝的动态帧视为“页面可能仍在动画或流式渲染”，不会立即消耗次数；系统会在不增加滚轮事件的前提下自适应等待页面稳定，单次最多 900ms，再决定是否重试。

合成器的条带列表按“页面顶部到页面底部”组织，并把页面 Y 显式换算为 Quartz 输出画布坐标。最终实现不再整体翻转画布；测试图必须先走 `NSBitmapImageRep → PNG → NSBitmapImageRep`，再按实际显示坐标读取顶部/底部像素。这样验证的是 AppKit 预览和保存文件的真实方向，而不是容易把错误抵消掉的 CGContext 内部坐标。

WebView/Electron 应用会忽略直接投递到进程的滚轮事件，因此自动滚动仍通过全局 HID 事件流发送，以截图区域中心坐标命中正确的滚动视图。发送前保存真实鼠标位置，发送后立即恢复；延迟 12 ms 再做一次兜底恢复，但只有光标仍停留在软件合成位置附近时才执行。如果期间检测到用户移动了鼠标，则不覆盖用户的新位置，使暂停、取消和完成保存可以正常点击。

成熟工具采用“运动检测”和“拼接检测”分层：先把滚动前后的稳定画面做独立比较，确认视口是否真的移动；只有确认移动后才要求接缝匹配。固定标题栏、输入框和小范围动态元素从运动判断中排除。连续两次确认主体区域没有位移才判断到底；画面有明显位移但暂时无法匹配接缝时，进入有上限的稳定等待，而不是提前判定到底或继续滚动造成缺页。

滚轮事件使用标准 `.line` 单位，每个事件限制为 3–10 行，不再发送 180–520 的超大 `.pixel` 单事件；每个逻辑滚动连续发送 2 个有界滚轮事件，与成熟工具的默认 ScrollAmount 思路一致。这样单步距离足够快，同时保持拼接重叠，并避免不同 App 对单次超大滚轮增量处理不一致。
